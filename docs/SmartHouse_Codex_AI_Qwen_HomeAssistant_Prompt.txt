Ты — senior backend/AI engineer и архитектор интеграций. Твоя задача — реализовать в проекте SmartHouse AI-ассистента на базе Qwen2.5, который получает актуальные данные из Home Assistant, умеет отвечать на вопросы пользователя о состоянии дома, выполнять разрешённые команды через контролируемый backend tool-layer и создавать предложения для автоматизаций.

ВАЖНО:
- Не давай Qwen прямой неограниченный доступ к Home Assistant.
- Все обращения к Home Assistant должны идти через backend и строго типизированный слой инструментов.
- Модель не должна выдумывать состояние дома.
- Если данных недостаточно — модель обязана запросить их через tools.
- Любые потенциально опасные действия должны требовать подтверждения пользователя.
- Реализация должна быть пригодна для дальнейшего подключения Flutter-клиента.
- Используй существующую архитектуру проекта, не переписывай всё без необходимости.
- Перед изменением кода сначала проанализируй структуру репозитория, существующие backend-модули, Home Assistant integration, auth, websocket, entities, rooms и API.
- Не удаляй уже работающий функционал.
- Если в проекте уже есть похожие классы/services/repositories/controllers — переиспользуй их.

2. ОБЩАЯ АРХИТЕКТУРА
==================================================

Использовать следующую схему:

Flutter SmartHouse
        |
        v
SmartHouse Backend API
        |
        v
AI Orchestrator
   |            |
   v            v
Qwen2.5      HA Tool Layer
                  |
                  v
          Home Assistant
       REST API + WebSocket

Qwen2.5:
- понимает естественный язык;
- выбирает нужный tool;
- анализирует результаты;
- формирует человеческий ответ;
- создаёт структурированные предложения автоматизаций.

Backend:
- хранит connection/auth к HA;
- проверяет права пользователя;
- нормализует entities;
- вызывает Home Assistant;
- валидирует tool arguments;
- подтверждает результат действия;
- не даёт модели выполнять произвольные HA service calls.

==================================================
9. ВЫПОЛНЕНИЕ КОМАНД
==================================================

Команды пользователя должны выполняться через backend.

Пример:

User:
"Выключи свет на кухне"

Qwen выбирает:
turn_off_device(...)

Backend:
1. resolve friendly name -> internal device/entity;
2. проверяет, что entity существует;
3. проверяет права пользователя;
4. проверяет, что action разрешён;
5. вызывает HA;
6. получает/ждёт подтверждение state через REST/WebSocket;
7. возвращает result модели.

Tool result:

{
  "success": true,
  "device": "Свет на кухне",
  "new_state": "off"
}

Только после этого Qwen отвечает:
"Свет на кухне выключен."

Если HA не подтвердил state:
"Команда отправлена, но Home Assistant пока не подтвердил новое состояние."

==================================================
10. УРОВНИ РИСКА
==================================================

Добавить action safety classification.

LOW RISK:
- light on/off;
- brightness;
- RGB;
- обычные media actions;
- запуск обычной scene;
- безопасная smart plug, если устройство не помечено critical.

MEDIUM:
- climate temperature;
- covers;
- некоторые power devices.

HIGH:
- door locks;
- security/alarm;
- гаражные ворота;
- удаление автоматизаций;
- критические реле;
- потенциально опасные устройства.

High-risk action не выполнять сразу.

Tool должен вернуть:

{
  "requires_confirmation": true,
  "confirmation_id": "...",
  "action": {
    ...
  }
}

Flutter показывает подтверждение.

После явного подтверждения пользователя:
POST /ai/confirm-action/:id

Только после этого backend выполняет действие.

Никогда не доверять строке "да" внутри самой модели без backend confirmation token.

12. AI SYSTEM PROMPT
==================================================

Создать отдельный system prompt файл.

Например:
src/ai/prompts/smart-house-assistant.txt

Основные правила system prompt:

Ты — SmartHouse Assistant.

Ты помогаешь пользователю управлять его умным домом.

Правила:

1. Никогда не выдумывай состояние дома.
2. Для любых фактов о доме используй tools.
3. Если tool не вернул данные — честно скажи, что данных недостаточно.
4. Никогда не называй entity_id пользователю, если это не advanced/debug mode.
5. Используй понятные названия комнат и устройств.
6. Пиши кратко.
7. При проблеме сначала сообщи факт, потом возможную причину.
8. Не утверждай причинность без достаточных данных.
9. Выполняй действия только через разрешённые tools.
10. Не пытайся вызвать произвольный Home Assistant service.
11. Для опасных действий требуй confirmation.
12. Если пользователь просит создать automation — сначала создай draft.
13. Если найдено несколько устройств с одинаковым названием — попроси уточнение.
14. Если пользователь говорит "включи свет", но непонятно где — используй conversational context, иначе уточни.
15. Не показывай внутренние JSON/tool calls пользователю.
16. Если Home Assistant недоступен — сообщи об этом.
17. Не подтверждай успешное действие, пока backend не вернул success.
18. Учитывай язык пользователя.
19. По умолчанию отвечай на русском, если пользователь пишет по-русски.
20. Не перегружай ответ техническими подробностями.

==================================================
31. DEFINITION OF DONE
==================================================

Функция считается готовой, когда:

1. Backend запускается.
2. Qwen provider подключается.
3. AI endpoint отвечает.
4. AI может запросить реальные HA данные через tools.
5. AI не получает HA token.
6. AI не выдумывает state при корректной работе tools.
7. "Что происходит дома?" работает.
8. "Где включён свет?" работает.
9. "Какая температура в комнате?" работает.
10. "Выключи свет" выполняется через HA tool.
11. Неизвестное устройство обрабатывается корректно.
12. Опасное действие требует confirmation.
13. Automation natural-language request создаёт draft.
14. Есть audit log.
15. Есть tests.
16. Есть документация.

==================================================
32. КРИТИЧЕСКИЕ ПРАВИЛА
==================================================

НЕ ДЕЛАТЬ:

- не давать Qwen прямой HA access token;
- не разрешать arbitrary service call;
- не отправлять модели весь HA state всегда;
- не полагаться на память модели для текущих данных;
- не выполнять lock/alarm действия без confirmation;
- не считать LLM output доверенным;
- не хранить secrets в коде;
- не создавать второй HA websocket client, если уже есть работающий;
- не переписывать существующий backend без причины;
- не ломать текущие API;
- не выдавать tool JSON пользователю как ответ;
- не утверждать "устройство выключено", пока backend это не подтвердил.

==================================================
33. ФИНАЛЬНЫЙ РЕЗУЛЬТАТ
==================================================

В результате в проекте должен появиться рабочий MVP SmartHouse AI Assistant:

Пользователь:
"Что сейчас происходит дома?"

AI -> tool -> Home Assistant -> AI:
"Дома всё в целом нормально. Температура 22,4 °C, влажность 46%. Включены три источника света. На кухне открыто окно, а у датчика ванной осталось 12% заряда."

Пользователь:
"Выключи свет на кухне."

AI -> backend tool -> HA -> state confirmation:
"Свет на кухне выключен."

Пользователь:
"Создай ночной свет в коридоре после 23:00."

AI:
создаёт валидируемый automation draft и отдаёт его Flutter для подтверждения.

Сначала проанализируй репозиторий и существующую архитектуру. Затем покажи короткий план изменений и начинай реализацию по этапам, не ломая уже существующий функционал.
